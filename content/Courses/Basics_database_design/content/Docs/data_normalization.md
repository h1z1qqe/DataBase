# Нормализация данных: простое руководство с примерами

**Нормализация** — это процесс **разбиения больших таблиц на несколько маленьких** так, чтобы устранить дублирование данных и избежать аномалий при вставке, обновлении и удалении. Проще говоря: «каждый факт хранится в одном месте».

Разберём на примере, который можно сразу выполнить в вашем контейнере.

---

## 🔹 Зачем нужна нормализация: три беды «плохой» таблицы

Представим интернет-магазин. Мы хотим хранить заказы и информацию о клиентах. Новичок часто делает **одну большую таблицу**:

```sql
CREATE DATABASE shop_norm
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;
USE shop_norm;

CREATE TABLE orders_bad (
    order_id      INT AUTO_INCREMENT PRIMARY KEY,
    customer_name VARCHAR(100),
    customer_city VARCHAR(100),
    product_name  VARCHAR(100),
    product_price INT,
    quantity      INT,
    order_date    DATE
);
```
Наполним данными:
```sql
INSERT INTO orders_bad (customer_name, customer_city, product_name, product_price, quantity, order_date) VALUES
  ('Иван',  'Москва',          'Яблоки',   120, 2, '2026-10-01'),
  ('Иван',  'Москва',          'Лимоны',   200, 1, '2026-10-01'),
  ('Мария', 'Казань',          'Яблоки',   120, 3, '2026-10-02'),
  ('Мария', 'Казань',          'Хурма',    350, 1, '2026-10-03'),
  ('Пётр',  'Санкт-Петербург', 'Каштаны',  200, 2, '2026-10-04');
```
**Что не так с этой таблицей?** Три классические аномалии:

### 🔴 Аномалия вставки (insert anomaly)
Нельзя добавить нового клиента, который ещё не сделал заказ. У него нет `order_id`, нет товара — строка не имеет смысла.

### 🔴 Аномалия обновления (update anomaly)
Иван живёт в Москве. Это записано **дважды** (в двух заказах). Если Иван переедет в Сочи — нужно обновить **обе** строки. Забудете одну — в базе будет противоречие: «Иван живёт и в Москве, и в Сочи».

### 🔴 Аномалия удаления (delete anomaly)
Если удалить последний заказ Марии, исчезнет и информация о том, что Мария из Казани. Клиент «пропадёт» из базы.

**Нормализация решает все три проблемы.**

---

## 🔹 Первая нормальная форма (1NF): атомарность

**Правило:** каждое значение в ячейке должно быть **атомарным** (неделимым). Никаких списков, массивов, «Иван, Пётр» в одной ячейке.

### ❌ Нарушение 1NF

```sql
CREATE TABLE orders_1nf_bad (
    order_id INT PRIMARY KEY,
    customer VARCHAR(100),
    products VARCHAR(255),  -- ← «Яблоки, Лимоны» в одной ячейке
    phones   VARCHAR(255)   -- ← «+7-999-111, +7-999-222» в одной ячейке
);
```

| order_id | customer | products | phones |
|----------|----------|----------|--------|
| 1 | Иван | Яблоки, Лимоны | +7-999-111, +7-999-222 |

**Проблема:** нельзя нормально фильтровать (`WHERE products = 'Яблоки'` не сработает), нельзя посчитать количество товаров, нельзя добавить индекс.

### ✅ Приведение к 1NF

Разбиваем составные значения на отдельные строки:

```sql
CREATE TABLE order_items_1nf (
    order_id     INT,
    customer     VARCHAR(100),
    product_name VARCHAR(100),
    phone        VARCHAR(20),
    PRIMARY KEY (order_id, product_name, phone)
);
```

| order_id | customer | product_name | phone |
|----------|----------|--------------|-------|
| 1 | Иван | Яблоки | +7-999-111 |
| 1 | Иван | Яблоки | +7-999-222 |
| 1 | Иван | Лимоны | +7-999-111 |
| 1 | Иван | Лимоны | +7-999-222 |

Теперь каждое значение атомарно. Но появилось **дублирование** — это уже задача 2NF и 3NF.

---

## 🔹 Вторая нормальная форма (2NF): полная зависимость от ключа

**Правило:** таблица в 1NF, и **каждый неключевой столбец зависит от всего первичного ключа целиком**, а не от его части.

Это актуально только для таблиц с **составным** первичным ключом.

### ❌ Нарушение 2NF

В таблице `order_items_1nf` ключ составной: `(order_id, product_name, phone)`. Но столбец `customer` зависит **только от `order_id`**, а не от всего ключа.

**Проблема:** имя клиента дублируется для каждой пары «товар-телефон» одного заказа. Если Иван сменит имя — править нужно много строк.

### ✅ Приведение к 2NF

Разделяем на две таблицы:

```sql
-- Заказы: клиент зависит только от order_id
CREATE TABLE orders_2nf (
    order_id INT PRIMARY KEY,
    customer VARCHAR(100)
);

-- Позиции заказа: товар и телефон зависят от составного ключа
CREATE TABLE order_items_2nf (
    order_id     INT,
    product_name VARCHAR(100),
    phone        VARCHAR(20),
    PRIMARY KEY (order_id, product_name, phone),
    FOREIGN KEY (order_id) REFERENCES orders_2nf(order_id)
);
```

**orders_2nf:**

| order_id | customer |
|----------|----------|
| 1 | Иван |

**order_items_2nf:**

| order_id | product_name | phone |
|----------|--------------|-------|
| 1 | Яблоки | +7-999-111 |
| 1 | Яблоки | +7-999-222 |
| 1 | Лимоны | +7-999-111 |
| 1 | Лимоны | +7-999-222 |

Теперь `customer` хранится **один раз** на заказ. Дублирование уменьшилось.

## 🔹 Третья нормальная форма (3NF): никаких транзитивных зависимостей

**Правило:** таблица в 2NF, и **ни один неключевой столбец не зависит от другого неключевого столбца**. То есть все неключевые столбцы зависят **только от ключа**.

### ❌ Нарушение 3NF

Вернёмся к `orders_bad`:

| order_id | customer_name | customer_city | product_name | product_price | quantity |
|----------|---------------|---------------|--------------|---------------|----------|
| 1 | Иван | Москва | Яблоки | 120 | 2 |

Здесь:
- `customer_city` зависит от `customer_name` (а не напрямую от `order_id`).
- `product_price` зависит от `product_name` (а не от `order_id`).

Это **транзитивные зависимости**: `order_id → customer_name → customer_city` и `order_id → product_name → product_price`.

**Проблема:** цена яблок записана в каждой строке, где есть яблоки. Изменится цена — править все строки.

### ✅ Приведение к 3NF

Разделяем на **четыре таблицы**:

```sql
-- Клиенты
CREATE TABLE customers_3nf (
    customer_id   INT AUTO_INCREMENT PRIMARY KEY,
    customer_name VARCHAR(100) NOT NULL,
    customer_city VARCHAR(100) NOT NULL
);

-- Товары
CREATE TABLE products_3nf (
    product_id    INT AUTO_INCREMENT PRIMARY KEY,
    product_name  VARCHAR(100) NOT NULL,
    product_price INT NOT NULL
);

-- Заказы (шапка)
CREATE TABLE orders_3nf (
    order_id    INT AUTO_INCREMENT PRIMARY KEY,
    customer_id INT NOT NULL,
    order_date  DATE NOT NULL,
    FOREIGN KEY (customer_id) REFERENCES customers_3nf(customer_id)
);

-- Позиции заказа (строки)
CREATE TABLE order_items_3nf (
    order_id   INT NOT NULL,
    product_id INT NOT NULL,
    quantity   INT NOT NULL,
    PRIMARY KEY (order_id, product_id),
    FOREIGN KEY (order_id)   REFERENCES orders_3nf(order_id),
    FOREIGN KEY (product_id) REFERENCES products_3nf(product_id)
);
```
Наполним:
```sql
INSERT INTO customers_3nf (customer_name, customer_city) VALUES
  ('Иван',  'Москва'),
  ('Мария', 'Казань'),
  ('Пётр',  'Санкт-Петербург');

INSERT INTO products_3nf (product_name, product_price) VALUES
  ('Яблоки',  120),
  ('Лимоны',  200),
  ('Хурма',   350),
  ('Каштаны', 200);

INSERT INTO orders_3nf (customer_id, order_date) VALUES
  (1, '2026-10-01'),  -- order_id = 1, Иван
  (2, '2026-10-02'),  -- order_id = 2, Мария
  (2, '2026-10-03'),  -- order_id = 3, Мария
  (3, '2026-10-04');  -- order_id = 4, Пётр

INSERT INTO order_items_3nf (order_id, product_id, quantity) VALUES
  (1, 1, 2),  -- Иван: Яблоки × 2
  (1, 2, 1),  -- Иван: Лимоны × 1
  (2, 1, 3),  -- Мария: Яблоки × 3
  (3, 3, 1),  -- Мария: Хурма × 1
  (4, 4, 2);  -- Пётр: Каштаны × 2
```

### Что мы получили

| Таблица | Что хранит | Дублирование |
|---------|-----------|--------------|
| `customers_3nf` | Клиенты (имя, город) | ❌ Нет |
| `products_3nf` | Товары (название, цена) | ❌ Нет |
| `orders_3nf` | Заказы (кто, когда) | ❌ Нет |
| `order_items_3nf` | Позиции (что, сколько) | ❌ Нет |

**Теперь:**
- Иван хранится **один раз**. Переезд → одно `UPDATE`.
- Цена яблок хранится **один раз**. Изменение → одно `UPDATE`.
- Можно добавить клиента без заказа. Можно добавить товар без продаж.
- Удаление заказа не удаляет клиента и товар.

## 🔹 Сравнение «до» и «после»

### Было (одна таблица `orders_bad`)

```sql
-- Сколько потратил Иван?
SELECT SUM(product_price * quantity)
FROM orders_bad
WHERE customer_name = 'Иван';
```
Работает, но данные дублируются, и любое изменение — риск аномалии.

### Стало (4 таблицы в 3NF)

```sql
-- Сколько потратил Иван?
SELECT SUM(p.product_price * oi.quantity) AS total
FROM customers_3nf c
JOIN orders_3nf o      ON c.customer_id = o.customer_id
JOIN order_items_3nf oi ON o.order_id = oi.order_id
JOIN products_3nf p    ON oi.product_id = p.product_id
WHERE c.customer_name = 'Иван';
```

Запрос длиннее, но:
- Нет дублирования.
- Нет аномалий.
- Легко добавить нового клиента или товар.

## 🔹 Нормальная форма Бойса-Кодда (BCNF) — кратко

BCNF — усиленная 3NF. Она требует, чтобы **каждый определитель был потенциальным ключом**. На практике большинство таблиц, приведённых к 3NF, уже находятся в BCNF. Нарушения возникают редко — в таблицах с несколькими составными ключами. Для начинающих достаточно знать: **3NF — это «рабочий стандарт»**, BCNF — уточнение для сложных случаев.

---

## 🔹 Денормализация: когда правила нарушают осознанно

Нормализация уменьшает дублирование, но **увеличивает количество `JOIN`**. Иногда это замедляет запросы. Тогда применяют **денормализацию** — сознательное добавление избыточности ради скорости.

**Пример:** в `orders_3nf` можно добавить вычисляемое поле `total_amount`:

```sql
ALTER TABLE orders_3nf ADD COLUMN total_amount INT DEFAULT 0;

UPDATE orders_3nf o
SET total_amount = (
    SELECT SUM(p.product_price * oi.quantity)
    FROM order_items_3nf oi
    JOIN products_3nf p ON oi.product_id = p.product_id
    WHERE oi.order_id = o.order_id
);
```

Теперь сумма заказа хранится **в двух местах**: в `order_items_3nf` (вычисляемая) и в `orders_3nf.total_amount` (сохранённая). Это дублирование, но оно ускоряет отчёты.

**Правило:** денормализуют **только после** того, как база приведена к 3NF, и **только при доказанной необходимости**.

## 📌 Итог

| Нормальная форма | Правило | Что устраняет |
|------------------|---------|---------------|
| **1NF** | Атомарные значения | Списки в ячейках |
| **2NF** | Зависимость от всего ключа | Частичные зависимости |
| **3NF** | Нет транзитивных зависимостей | Зависимости неключевых друг от друга |
| **BCNF** | Каждый определитель — ключ | Редкие сложные случаи |
| **Денормализация** | Осознанная избыточность | Замедление из-за `JOIN` |

**Главная мысль:** нормализация — это не «максимальное количество таблиц», а **устранение аномалий**. Каждый факт должен храниться в одном месте. Если правило нарушено — вы либо получите противоречивые данные, либо не сможете что-то добавить или удалить без потерь.
