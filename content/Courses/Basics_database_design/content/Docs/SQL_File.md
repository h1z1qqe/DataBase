# Является ли база данных SQL «физически» .sql-файлом?

**Короткий ответ: нет.** `.sql`-файл — это **текстовый файл с командами** (скрипт или дамп), а не сама база данных. Физически база данных — это **набор бинарных файлов**, которыми управляет СУБД. Разберём это подробно, потому что путаница очень распространена.

---

## 🔹 1. Что такое `.sql`-файл

`.sql`-файл — это обычный **текстовый файл**, внутри которого записаны SQL-команды:

```sql
CREATE DATABASE sql_practice;
USE sql_practice;

CREATE TABLE customers (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL
);

INSERT INTO customers (name) VALUES ('Иван Иванов');
```

Такой файл **не содержит данных в том виде, в котором их хранит СУБД**. Это просто инструкции: «создай базу», «создай таблицу», «вставь строку».

**Когда `.sql`-файл используют:**
- **Дамп (dump)** — экспорт базы в виде SQL-команд для резервной копии или переноса.
- **Скрипт инициализации** — файл, который выполняется при первом запуске контейнера, чтобы создать схему и наполнить её данными.
- **Миграции** — файлы с изменениями структуры БД.

**Как выполнить `.sql`-файл:**
```bash
# Изнутри контейнера
docker exec -i my-mysql mysql -uroot -p123 < dump.sql

# Или через клиент mysql
mysql> SOURCE /path/to/dump.sql;
```

После выполнения команды **файл больше не нужен** — данные уже внутри СУБД.

## 🔹 2. Как база данных хранится «физически»

Физическое представление зависит от **СУБД** и **движка хранения**. Рассмотрим MySQL (с которым вы работаете) и движок **InnoDB** (по умолчанию).

### Внутри контейнера `my-mysql`

Ваш volume `mysql_data` смонтирован в `/var/lib/mysql`. Именно там лежат **физические файлы** базы:

```bash
docker exec -it my-mysql ls -la /var/lib/mysql
```

Вы увидите примерно такую картину:

```
drwxr-xr-x  mysql mysql  ibdata1
drwxr-xr-x  mysql mysql  ib_logfile0
drwxr-xr-x  mysql mysql  ib_logfile1
drwxr-xr-x  mysql mysql  #innodb_temp
drwxr-xr-x  mysql mysql  mysql/
drwxr-xr-x  mysql mysql  performance_schema/
drwxr-xr-x  mysql mysql  sys/
drwxr-xr-x  mysql mysql  sql_practice/
```

### Что это за файлы

| Файл / каталог | Что содержит |
|----------------|--------------|
| `ibdata1` | Системное табличное пространство InnoDB: метаданные, undo-логи, буфер |
| `ib_logfile0`, `ib_logfile1` | **Redo-логи** — журнал для восстановления после сбоев |
| `mysql/` | Системная база данных (пользователи, привилегии) |
| `performance_schema/` | Системная база для мониторинга производительности |
| `sys/` | Системная база с удобными представлениями |
| `sql_practice/` | **Ваша база данных** — каталог с файлами таблиц |

### Внутри каталога `sql_practice/`

```bash
docker exec -it my-mysql ls -la /var/lib/mysql/sql_practice
```

Вы увидите:

```
customers.ibd
orders.ibd
```

| Файл | Что содержит |
|------|--------------|
| `customers.ibd` | **Табличное пространство** таблицы `customers`: данные + индексы в бинарном формате |
| `orders.ibd` | То же для таблицы `orders` |

Расширение `.ibd` — это **InnoDB data file**. Внутри — страницы по 16 КБ, B-деревья индексов, строки таблицы в бинарном виде. **Человекочитаемого SQL там нет.**

### Дополнительные файлы (могут появляться)

| Файл | Назначение |
|------|------------|
| `*.ibd` | Данные и индексы таблицы (InnoDB) |
| `*.frm` | Метаданные таблицы (в MySQL 8.0+ **убраны**, заменены data dictionary в InnoDB) |
| `binlog.000001` | **Бинарный лог** — журнал всех изменений (для репликации и point-in-time recovery) |
| `*.err` | Лог ошибок сервера |
| `*.pid` | PID-файл процесса `mysqld` |
| `ibtmp1` | Временное табличное пространство |

## 🔹 3. Схема: от SQL-команды до файла на диске

```
Вы пишете:                          СУБД делает:
─────────────────                   ─────────────────────────────────
CREATE TABLE customers (...)  ───►  Создаёт файл customers.ibd
                                    (табличное пространство)

INSERT INTO customers ...     ───►  Пишет строку в страницу данных
                                    внутри customers.ibd
                                    + запись в redo-log (ib_logfile0)
                                    + запись в binlog (binlog.000001)

SELECT * FROM customers       ───►  Читает страницы из customers.ibd
                                    (или из буферного пула в памяти)
```

**Ключевая мысль:** SQL — это **интерфейс**. Вы говорите с СУБД на языке SQL, а она **переводит** ваши команды в операции с бинарными файлами.

## 🔹 4. Что происходит при экспорте в `.sql`

Когда вы делаете дамп:

```bash
docker exec my-mysql mysqldump -uroot -p123 sql_practice > dump.sql
```

СУБД:
1. Читает бинарные файлы `customers.ibd`, `orders.ibd`.
2. **Преобразует** данные обратно в текстовые SQL-команды (`CREATE TABLE`, `INSERT`).
3. Записывает их в `dump.sql`.

То есть `.sql`-файл — это **не физическое представление**, а **текстовая реконструкция** базы. Его можно открыть в блокноте и прочитать, но сама база так не хранится.

**Обратный процесс (восстановление):**
```bash
docker exec -i my-mysql mysql -uroot -p123 < dump.sql
```
СУБД читает SQL-команды и **создаёт бинарные файлы заново**.

## 🔹 5. А как у других СУБД?

Физическое представление зависит от СУБД:

| СУБД | Физическое хранение |
|------|---------------------|
| **MySQL (InnoDB)** | `*.ibd` (табличные пространства), `ibdata1`, redo-логи, binlog |
| **MySQL (MyISAM)** | `*.MYD` (данные), `*.MYI` (индексы), `*.frm` (схема) |
| **PostgreSQL** | Каталог `base/` с файлами по OID таблиц, WAL-логи в `pg_wal/` |
| **SQLite** | **Один файл** `*.sqlite` или `*.db` (вся база в одном файле) |
| **Oracle** | Табличные пространства (`.dbf`), redo-логи, control-файлы |
| **SQL Server** | `*.mdf` (данные), `*.ldf` (журнал транзакций) |

**Интересный случай — SQLite:** там база действительно представлена **одним файлом** (обычно `.sqlite` или `.db`). Но и он **не текстовый** — это бинарный формат. Прочитать его в блокноте нельзя.

---

## 🔹 6. Почему возникает путаница

Путаница возникает из-за трёх вещей:

1. **`.sql`-файлы часто лежат рядом с проектом** — например, в репозитории (`schema.sql`, `seed.sql`). Кажется, что это и есть база.
2. **Дампы выглядят как база** — внутри `dump.sql` видно `CREATE TABLE` и `INSERT`, и создаётся ощущение, что «вот она, база».
3. **SQLite** — единственная популярная СУБД, где база = один файл. Но и там это не `.sql`, а бинарный `.sqlite`.

## 🔹 7. Практический вывод для вашего Docker-контейнера

| Что | Где лежит | Формат |
|-----|-----------|--------|
| **База данных** | Volume `mysql_data` → `/var/lib/mysql/` | Бинарные файлы (`*.ibd`, `ibdata1`, логи) |
| **Дамп (резервная копия)** | `dump.sql` на хосте | Текстовый SQL-скрипт |
| **Скрипт инициализации** | `init.sql` (монтируется в `/docker-entrypoint-initdb.d/`) | Текстовый SQL-скрипт |

**Если вы удалите `dump.sql`** — база **не пострадает**, она в volume.
**Если вы удалите volume `mysql_data`** — база **исчезнет**, даже если `dump.sql` остался (но из дампа её можно восстановить).

## 📌 Итог

| Утверждение | Верно? |
|-------------|--------|
| «База данных SQL — это `.sql`-файл» | ❌ Нет |
| «`.sql`-файл — это скрипт или дамп, а не сама база» | ✅ Да |
| «Физически база — это набор бинарных файлов, которыми управляет СУБД» | ✅ Да |
| «Для MySQL это `*.ibd`, `ibdata1`, логи в `/var/lib/mysql/`» | ✅ Да |
| «SQLite хранит базу в одном бинарном файле, но не в `.sql`» | ✅ Да |
| «Из `.sql`-дампа можно восстановить базу» | ✅ Да |

**Главная мысль:** `.sql` — это **язык общения** с базой и **формат резервной копии**, а не её физическое тело. Тело базы — бинарные файлы, которые СУБД читает и пишет, а вы видите только результат через SQL-запросы.
